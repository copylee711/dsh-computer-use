# 0.6.0 验证记录

日期：2026-10-04。本版的目标是缩短完成任务的总耗时，做法参考了 [wwwort/dsh-win-computer-use](https://github.com/wwwort/dsh-win-computer-use)，取舍以实测为准。

## 改了什么

| 改动 | 说明 |
|---|---|
| `target` | 点击、输入、滚动、移动可以用控件名称代替坐标；先找窗口本身，找不到再找它弹出的菜单；最多等 3 秒控件出现，重名时列出候选而不猜 |
| `wait` 的 `until` | 等窗口或控件出现（或消失）就继续，不再猜时长；对话框按前台窗口识别，应用按 `open_application` 的同一套别名识别 |
| 读文本 | `ui_elements` 的 `text: true`、`computer_batch` 的 `finish: "text"` |
| 批次末尾 `zoom` | 省掉批次后单独放大的一次调用 |
| 打开应用提速 | 判断应用是否在后台运行时不再查托盘图标（1.5–2.5 秒 → 约 10 毫秒）；开始菜单索引在 helper 启动时预热（首次约 2 秒 → 约 5 毫秒），缓存 10 分钟；等窗口出现的轮询间隔 250 → 100 毫秒 |
| 少等一次 | 批次以 `wait` 结尾时，不再为结尾截图重复等待画面稳定 |

## 试过但撤掉的

**在批次里直接打开应用**（一次调用从打开应用做到底）。模型确实会这样用，但应用刚打开时是什么状态它没看过：记事本会恢复上次的标签页，盲打的文字进了旧标签页，Ctrl+S 不弹“另存为”，整批失败后重来。记事本任务的中位耗时从约 70 秒变成 97 秒，所以打开应用仍然是单独一次调用，模型看到窗口后再批量操作。

## 自动检查

- `pnpm typecheck`、`pnpm test`（9 个文件 98 项）通过。新增 `tests/target.spec.ts`（名称匹配的优先级、歧义、禁用控件、候选建议）和 `tests/tools.spec.ts` 里的 11 项（按名称点击、等控件出现、重名报候选、输入前先点输入框、条件等待成功与超时、等控件消失、对话框识别、批次末尾放大、以文本结尾、失败时仍给截图、读窗口文本）。
- `node scripts/helper-smoke.mjs --notepad`（真实屏幕，只操作脚本自己的临时文件）：`text` 命令读回记事本内容 63 毫秒；按名称找到“文件”菜单 65 毫秒；点开后在弹出菜单里找到“另存为”。

## 真实模型对比

隔离的 `dsh web` 0.2.0-rc.2，三个固定任务，每次新开会话，任务自带结果校验（文件内容 / 计算结果 / 文件数），全部运行都通过了校验。模型为 DeepSeek V4.1 Flash，经 opencode go 线路；`pauseOnUserInput` 关闭、`accessMode` 为全部允许，新旧两版相同。

- 记事本：新建文档，输入一行字，另存到指定路径，关闭。
- 计算器：算 1234 × 5678 并报告结果，关闭。
- 资源管理器：打开指定文件夹，报告其中 `.ts` 文件数，关闭窗口。

最终一组（新旧交错运行，每项 3 次；“旧”是已发布的 0.5.2）：

| 任务 | 版本 | 请求轮数（中位 / 平均） | 总耗时秒（中位 / 平均） | 输入 token 千（中位） |
|---|---|---|---|---|
| 计算器 | 旧 | 7 / 6.0 | 43.8 / 40 | 118 |
| 计算器 | 新 | 5 / 5.0 | 29.2 / 30 | 79 |
| 资源管理器 | 旧 | 9 / 8.3 | 40.3 / 42 | 143 |
| 资源管理器 | 新 | 6 / 6.7 | 40.3 / 40 | 98 |
| 记事本 | 旧 | 10 / 13.7 | 54.8 / 88 | 182 |
| 记事本 | 新 | 7 / 7.7 | 58.4 / 54 | 123 |

怎么读这些数：

- 轮数和 token 的下降在几组运行里都重复出现（另一组每项 4 次：记事本 9.5 → 6.5 轮，资源管理器 6.5 → 5.5 轮，计算器持平）。
- 总耗时没有变慢，平均值更好，但每项只有 3 次，单次波动很大（同一版本、同一任务可以差一倍以上，旧版记事本有一次 168 秒）。**不能据此说“耗时显著缩短”**，只能说没有变差、轮数更少。
- 最后一处改动（先扫窗口、需要时才扫弹出菜单）之后只补跑了每项 2 次，全部通过，工具侧耗时在记事本任务里从约 22 秒降到 12–16 秒；这两次的总耗时仍被模型延迟主导。

## 时间花在哪

按会话日志里每一步的时间戳拆分：

- 模型响应：每轮 3–8 秒，偶尔 25 秒以上，占总耗时的六到七成。
- 工具执行：打开应用 4–5 秒（应用自身启动加等画面稳定），其余每次调用 1–3 秒。

同一版本换成 DeepSeek 官方接口各跑一次：计算器 16.5 秒、资源管理器 18.3 秒、记事本 34.7 秒，模型响应合计 7.5–13.5 秒，约为 opencode go 线路的一半。也就是说，**线路的响应速度对总耗时的影响大于本版全部改动**。

## 桌面版实测（官方模型）

在用户日常使用的 DSH 桌面版 0.2.0-rc.2 里装入本版，模型为 DeepSeek 官方账号的 V4.1 Flash（思考强度 High），按应用授权、迷你进度卡片等均为用户平时的设置。任务：“打开Chrome，进入github，点进我最近的pull request”。

- 结果正确：Chrome 停在用户最近更新的 Pull Request 页面。
- 全程 27.4 秒，7 轮请求；模型响应合计 15.0 秒，工具执行合计 12.0 秒。
- 过程：申请操控 Chrome（完全权限下自动通过）→ `open_application` 把已在运行的 Chrome 调到前台（3.6 秒）→ 一次批量调用新开标签页、输入“我的 PR，按更新时间排序”的地址并回车 → 等页面加载 → **用 `target` 按链接标题点进第一条 PR** → **用 `wait until window` 确认页面标题已变** → 回复结果。

## 没有验证的

- 每项样本只有 2–4 次，结论限于“未变差、轮数减少”。
- 只测了记事本、计算器、资源管理器三个原生应用；浏览器、Office、Electron 应用里 `target` 的命中率没有测。
- 按应用授权模式下的批量流程、多显示器、非视觉模型没有重跑真实模型，只有单元测试。
- 桌面版只跑了上面这一个任务一次。

## 0.6.1

来自用户在桌面版实测“打开我的word，打字写一篇寓言故事”的会话记录（7 轮、38 秒，其中模型响应 24.7 秒、工具 13.0 秒）。

| 现象 | 原因 | 改动 |
|---|---|---|
| 选了“流式”，357 字却一次贴上去 | 分块只认空行分段；这段文字每段之间只有一个换行，被当成一整块 | 全文没有空行时按行分块（表格和代码块仍保持整块） |
| 设置页“预览效果”还是提示条，不是迷你进度卡片 | 预览没有带上 `hostWindow` 设置 | 预览与真实操控用同一组参数，迷你卡片模式下显示卡片和示例内容，持续 4 秒 |
| 动作之间不连贯 | 多走了几轮：先截图再打开应用；窗口出现后截图太早，画面没画完，又单独等了一次；输入和排版分成两批 | 提示改为直接 `open_application`、不要为了“看一眼”拆批；`wait until` 成功后先等画面稳定再返回 |
| 会话不弹审批时仍要先 `request_access` | 模型直接 `open_application` 会被拒绝，多一轮 | 会话策略为“从不询问”时，`open_application` 直接授权该应用（DeepSeek Harness 自身和禁用列表仍然不可操作） |

验证：`pnpm typecheck`、`pnpm test`（10 个文件 103 项）通过。在用户的桌面版里重跑同类任务两次，流式输入分别报告“streamed in 3 blocks”“streamed in 4 blocks”，文档内容和分段正确。

没有验证的：

- 预览里的迷你卡片没有亲眼确认。卡片对截图不可见（这是它的设计），只能确认调用与真实操控时相同。
- “不弹审批时直接授权”只有单元测试；两次实测里模型都先调用了 `request_access`。
- 两次桌面实测的耗时（199 秒、107 秒）不能用来和 0.6.0 比较：监控用的屏幕控制工具自己的全屏窗口盖住了屏幕，agent 的截图里看到的是它，多花了很多轮去排查。

## 0.7.0：操作时不深度思考

新增设置 `quickSteps`（默认关）。开启后，如果一次模型请求紧跟在本插件工具的结果之后（也就是 agent 正在操作电脑），就把这次请求的思考强度换成该模型提供的最低一档（依次找 `off`、`none`、`disabled`、`minimal`、`low`）；其余请求不动。请求对象是冻结的，所以做法是复制一份改过思考强度的请求，经同一个 `llm` 服务发出。

验证：

- `pnpm typecheck`、`pnpm test`（11 个文件 107 项）通过，新增 `tests/effort.spec.ts`。
- 隔离的 `dsh web` 0.2.0-rc.2，DeepSeek 官方接口，会话思考强度 high，计算器和记事本两个任务各 2 次，开与关各一组，全部通过任务自带校验。
  - 开启时，每个任务只有第一轮有思考内容（113–294 字），之后各轮思考内容为 0；关闭时各轮都有（最多 1751 字）。
  - 开启时每轮模型响应 0.7–1.9 秒。
- 第一次实现直接改请求对象，宿主报 `Cannot assign to read only property 'reasoningEffort'`，四次运行全部失败；改为复制后通过。

没有验证的：

- 这组对比里官方接口在 high 下本来就想得不多（每轮 1–3 秒），所以总耗时差别在波动范围内，说明不了提速幅度；用户在桌面版把整个会话设为 off 时观察到明显变快，那种“每轮思考几千字”的情形这里没有复现。
- 只测了 DeepSeek 官方接口。别的服务商在同一轮工具调用中途改变思考强度是否被接受没有测，所以默认关闭。
- 关闭思考后的操作准确率没有系统比较，每项只有 2 次。

## 0.7.1：设置页自动保存

用户反馈“操作时不深度思考”开了以后再回到设置页又变回关闭。原因：设置页的改动要点页面最底部的“保存”才写入，开关在页面中部，切换后直接离开就丢了（用户配置文件里没有 `quickSteps` 这一项，说明没有发生过保存）。改为每次改动 0.5 秒后自动保存，去掉“保存”“放弃修改”按钮；数值超出范围时不保存并提示；保存失败时显示“重试保存”。

验证（隔离的 `dsh web` 0.2.0-rc.2，真实设置页）：

- 切换开关后配置文件立即出现 `quickSteps: true`，刷新页面后开关仍为开启。
- 在“禁止操控的应用”里输入一行并回车，内容被保存，输入框里的换行没有被重置掉。
- 数值填成范围外的值时出现提示且不保存。
- `pnpm typecheck`、`pnpm test`（11 个文件 107 项）通过。

### quickSteps 在 opencode go 上的情况

opencode go 的 DeepSeek V4.1 Flash 只提供 Low / High / Max（界面上的 Default 是“不指定”），没有 Off，所以开启后用的是 Low。计算器任务各 1 次：

| 配置 | 步数 | 总耗时 | 各轮思考字数 |
|---|---|---|---|
| 关 | 5 | 21.9 秒 | 226 / 1588 / 104 / 152 / 0 |
| 开（降到 Low） | 6 | 32.8 秒 | 513 / 244 / 1856 / 137 / 166 / 0 |
| 给模型另外声明 Off、开（思考为 0） | 15 | 74.7 秒 | 全部为 0 |
| 给模型另外声明 Off、关 | 5 | 25.6 秒 | 326 / 443 / 123 / 0 / 0 |

结论：Low 并没有让它少想；这条线路每轮 2.5–5 秒，与是否思考关系不大；完全不思考的那一次多走了 10 步。每种只有 1 次，只能说明在 opencode go 上这个开关没有可见收益。

## 0.7.2：quickSteps 在同一轮里保持到底

用户在桌面版用官方模型开启 quickSteps 后，任务做完了但本轮以 `The content[].thinking in the thinking mode must be passed back to the API`（INVALID_REQUEST）结束。会话日志：操作电脑的几步思考为 0，随后模型调用了命令行工具核对文件；命令行结果之后的那次请求不再紧跟本插件的工具，于是恢复了思考，而 DeepSeek 在思考模式下要求本轮此前带工具调用的回复都带着思考内容，前面那几步没有，请求被拒。

修改：只要本轮（用户最后一条消息之后）出现过本插件工具的结果，本轮之后的所有请求都保持最低思考强度。下一轮从用户的新消息开始，恢复会话的思考强度。

验证（隔离的 `dsh web` 0.2.0-rc.2，DeepSeek 官方接口，任务为“计算器算数后关闭，再用命令行看时间”）：

- 开启 quickSteps 跑 3 次：操作之后调用命令行的那些请求思考均为 0，没有再出现 INVALID_REQUEST。
- 其中 2 次接着发了第二轮提问：第二轮恢复思考（309、482 字）并正常完成，说明上一轮不带思考的回复不影响下一轮。
- `pnpm typecheck`、`pnpm test`（11 个文件 108 项）通过。

发现但没有解决的：

- 开启 quickSteps 的 3 次里有 2 次，本轮因 `DeepSeek Messages stream: tool input is invalid JSON`（MALFORMED_RESPONSE）结束，都发生在不思考的步骤上；关闭 quickSteps 的 3 次对照没有出现。样本很小，但指向“不思考时模型更容易写坏工具参数”。0.7.0 的 4 次开启测试里没有出现过。
- 每步模型耗时：开启 1.0–2.0 秒，关闭 0.8–3.5 秒（个别 5.5 秒）。
